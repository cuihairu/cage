## 条目 1:Web UI 形态 / 引用联动 / 环境折叠(design-prototypes.md §III)

**条目来源**:`todo.md:1443`(「待用户拍板:Web UI 形态 / 引用联动 / 环境折叠」)+ `docs/design-prototypes.md:82-87`(§III Open decisions 三条)。

**背景(教学性)**:2026-10-12 起本仓给 `cage web` 做过三个 HTML 静态原型(init 问答流程、校验结果可视化),原型只是设计稿、不接代码。设计稿 §III 留了三条待拍板问题:①要不要把 Web 从「只做 Schema 编辑器」扩展成「也能做配置表单/校验结果界面」;②结构树视图里点一个引用(如 `Ref(Item.id)`)要不要跳到被引用的表;③环境差异热力图里,相邻环境值相同时要不要折叠显示。

**推荐决策**:
1. **Web UI 形态 → 采用「扩展既有 `cage web` 做 Web UI 表单」**。此条**已被 2026-10-20「规则配置界面」实际落地兑现**(`docs/ui.md`「Planner Rule Interface」节 + `cage serve`/`cage web` 的 `/status/` 页:数据表格视图 + 诊断过滤 + 点位高亮 + 上传替换 + 一键校验),即当时的决策就是「扩展既有 Web」而非「另起 CLI+MCP 双前端 + Web 只做编辑器」。本册确认该结论,不再重复立项。
2. **引用联动(结构树跨表引用跳转)→ 延后**。当前交付面的 Web 没有「结构树」视图(实际交付的是数据面板 + 诊断面板);策划最核心的诉求「点诊断跳到出错的行/列」已由既有**诊断点位高亮**(`docs/public/status/app.js` `jumpToDiag`)覆盖;Schema 结构浏览职责已由编辑器页承担。跨表引用跳转是「锦上添花」,且它依赖一个从未落地的结构树视图——为它新建视图不划算。
3. **环境折叠(热力图相邻环境折叠)→ 延后**。当前 Web 无「环境差异热力图」视图;环境差异已由「构建状态」卡片(每 profile×env 一张)+「对比」节(diff 两次构建)呈现,信息可达;热力图 + 折叠是低价值可视化,收益抵不上新增渲染面。

**理由**:
- **成本**:确认 #1 零成本(已落地);#2/#3 若做需新增结构树/热力图两个前端渲染面 + 对应 API 数据,约一人日级别,且与既有编辑器/数据面板职责重叠。
- **收益**:延后 #2/#3 不损失当前策划主链路(定位到出错行列已可用);确认 #1 让「策划不碰 CLI」的定位成立。
- **风险**:不建结构树/热力图视图 → 无行为回归风险(纯记录,不动代码);若后续真实需求出现(策划要可视化跨表关系),可随时按此记录重启,无需推翻本决策。

**立即执行动作**:在 `docs/design-prototypes.md` §III 标注三条已决(见下);`todo.md:1443` 追加「已代决」注记。
✅ 已执行(25ba0e6):§III「Decided 2026-10-30」块与 todo 注记均已落。
**不做/延后**:不新建「结构树视图」「环境差异热力图视图」——现有数据面板 + 诊断点位高亮 + 构建状态 + 对比节已覆盖策划需求;跨表引用跳转与环境折叠等可视化待真实需求出现再议。

## 条目 2:表三评估三项——快照验签 / LSP 未保存缓冲 / DB 行数预算(2026-10-18 审核整改)

**条目来源**:`todo.md:1606-1622`(审核整改表三「值得补的能力」:只做评估与分期建议,三项均待用户拍板)。

**背景(教学性)**:2026-10-18 独立审核把三件事评估为「值得补的能力」并给了分期建议,但按纪律「只评估不实现,需用户拍板」。三件事是:①快照签名与强制验签(快照包能否证明来源可信);②LSP 未保存缓冲诊断(编辑器里还没保存的内容能不能也报错);③DB 行数/字节预算与 PG 流式(超大数据库表会不会把内存吃爆)。

**推荐决策**:采纳审核给出的**分期建议**为实施计划,一期先做低风险、默认关闭的部分,二期/延后再议重头。

- **① 快照签名与强制验签 → 一期做「加载侧可选 `--require-signature`」,二期再议密钥分发**。验签实现复用既有 registry bundle/签名路径(`registry.rs` 已有 ed25519 签名门),签名走既有 bundle/presign 流程。**明确不做**:默认强制验签——引入密钥管理(签发方/存放/轮换)超出「单机工具」定位,会吓退单用户使用。
- **② LSP 未保存缓冲诊断 → 一期做「didChange 缓冲落临时文件」最简实现**(零校验管线改动,语义等价),再评估是否值得真内存化。**延后**:真内存化要改校验管线全链的文件锚定(loaders 全链),改动面广、收益边际。
- **③ DB 行数/字节预算与 PG 流式 → 一期做「行数 + 字节 ceiling」**(超限报错,复用 web 8 MiB 预算思路);**PG 真流式缓行**——收益依赖超大表场景,与「配置源定位(设计期人工维护规模)」不符。

**理由**:
- **成本**:三项一期均小改动、复用既有组件(签名门 / 临时文件 / 预算常量),每项约小时级;无新依赖。
- **收益**:①让快照来源可信成为可选能力(分发场景用得上);②编辑器实时诊断覆盖未保存内容,体验提升;③防超大表把内存吃爆(失败比 OOM 好)。
- **风险**:全部为**可选开关、默认关闭**,默认行为与字节确定性契约零变化;真流式 / 真内存化 / 密钥分发被明确延后,不冒进。

**立即执行动作**:记录本决策(本文件);三项一期实现列为**下一实施批次**(属功能实现,非本决策批的「立即动作」范畴)。
✅ 已执行(25ba0e6):决策已记录;一期三项为可选默认关,列入下一实施批次,**本批不实现**(见「不做/延后」)。
**不做/延后**:不做默认强制验签;不做 LSP 真内存化(一期先落临时文件);不做 PG 真流式(一期 ceiling 足够);密钥分发、内存化、流式均待真实需求/规模再议。
