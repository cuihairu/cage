## 一、总账（四段式）

**① 三桶计数。** 共登记 **32** 项差异：

- **文档超前于码（最危险）**：**4** 项 —— 文档写了源码没有/未实现的能力或参数，以文档为准会审出幽灵功能。
- **码超前于文档**：**10** 项 —— 源码已有、文档漏写，以文档为准会漏掉真功能。
- **描述不符**：**18** 项 —— 双方都有但口径不一致（参数 / 计数 / 错误码 / 路径 / 措辞）。

**② P0 清单。** **0 项。** 无任何差异造成数据损坏、安全暴露或不可逆后果；最接近 P0 的「文档超前」
四项（D01–D04）均为 CLI 命令示例或能力类别虚报，会让照文档操作的用户跑出失败命令或误信幽灵能力，
已定 **P1** 并当场改净，故无 P0 残留。

**③ 修复动作。** 全部 32 项当场修复（文档侧，源码为真相），改动覆盖 **27** 个文档文件
（README、README.zh + docs/ 下 25 页），新增 docs/审计-文档一致性.md 本表。无一处改动源码；
两处代码侧观察项登记为后续待办（见 D10、D22 备注）。

**④ 验证与闭环。** 修复后本地跑 `npm run docs:build`（VitePress）**通过**（19.0s，构建完整无错）；
`cargo test` 基线在代码深审阶段复核（本表仅文档侧改动，不触发 Rust 测试变更）。按六步法第 6 步闭环：

## 三、分桶说明

**文档超前于码（4 项，D01–D04）**：均集中在 CLI 命令示例与能力类别虚报。根源是命令签名在代码里演进
（verify 收敛为单 path；schema-draft/migrate-draft 重构参数）后文档未同步。最危险处是 D04——文档把
E1411 同时记为「类型」与「兼容性」两个类别，读者会误以为存在一个独立的引用类型检查面。

**码超前于文档（10 项，D16/D17/D19/D20/D21/D22/D24/D27/D29/D31）**：多为后交付功能未写入对应文档页
（FlatBuffers/JSON Schema/MessagePack/LSP/声明式规则码表/HASHES 路径安全/Excel 元行约定英文页）。
按规范以源码为真相补文档。

**描述不符（18 项，D05–D15/D18/D23/D25/D26/D28/D30/D32）**：计数（19→20 字段类型、web 测试数、基线
体积、示例产物数）与口径（E1201→E1202、E2202→E2201、`\r` 含行内、separator 支持 TaggedUnion、
xlsm 合并回填、E1301/E1401 渲染格式、安装输出文案、设计文档引用、README 徽章区）过时或错误。
全部以源码口径改正。
